# GitHub PR-Based Collaborative Documents — Tasks

Source of truth: `docs/ears/github-pr-collaborative-documents.md` (acceptance IDs `R-x.y`) and `docs/lld/github-pr-collaborative-documents.md` (architecture, build order). Source paths below are relative to `packages/visual-spec/`.

**Build order.** Phase 0 pins the two invariants everything else assumes (`nodeId` survives a live editor; local mode does not regress). Then the foundation — protocol types and the owned-node layer — because both the store and the renderer depend on `nodeId` existing. The **renderer (Unit 7) is the critical path**: it is the largest single item, nothing about reviewing works without it, and it can start as soon as the node layer lands. The GitHub adapter (Unit 4) is fully independent and can run in parallel from day one.

**Parallel lanes once Phase 1 lands:**
- Lane A — renderer + reviewer UI (7.x, 11.x) ← longest, start first
- Lane B — GitHub adapter + comment projection (4.x, 5.x)
- Lane C — document store + jobs (3.x, 8.x)

**Do not touch** `ui/anchor-resolver.ts`, `ui/markdown-surface.tsx`, or the local comment path. Collaboration uses a separate resolver and a separate renderer by design (R-6.6, R-10.6); sharing them is what puts R-10.1 at risk.

## Unit 2: Owned node layer

- [x] 2.1 NodeState-based `nodeId` + per-class transforms (deps: 0.1, 1.1, est: ~1w)
  - **RE-SCOPED after task 0.1.** The original title was "Owned block node classes carrying `nodeId`". Task 0.1 proved node replacement cannot keep the base `getType()` on Lexical 0.40, so R-2.2 now mandates Lexical's NodeState API instead. See the amended R-2.2 note in the EARS spec and the superseded-mechanism note in LLD §2.
  - why: serialized Lexical nodes have no stable key. A node transform registered per concrete class is the interception point that covers nodes created *inside* the editor — on Enter, on paste, on list toggle — and NodeState is the only carrier that survives serialization without changing the node's `type`.
  - acceptance: R-2.2 — `nodeId` carried via `createState`/`$setState`/`$getState`, assigned by `registerNodeTransform` per concrete class, not a structural path or sidecar map; R-2.3 — the serialized `type` stays the base string so `MARKDOWN_SUPPORTED_NODE_TYPES` and the transformers keep matching (free under NodeState); R-2.4 — every editor-created node gets a document-unique `nodeId`; R-2.5 — `nodeId` survives `exportJSON()`/`importJSON()`.
  - verify: extend the 0.1 harness (`ui/node-identity.contract.test.tsx`) across every block type in `MARKDOWN_SUPPORTED_NODE_TYPES` (R-12.2). Note `registerNodeTransform` rejects abstract bases like `ElementNode` — one call per concrete class.
  - landed: `ui/node-id-extension.ts` (new) + `ui/node-id-extension.contract.test.tsx` (new, 22 tests). Suite 397 → 419 green, `tsc --noEmit` clean. Exports `nodeIdState`, `NODE_ID_BLOCK_TYPES`, `NODE_ID_EXCLUDED_TYPES`, `NODE_ID_UNSERIALIZABLE_TYPES`, `$getNodeId`, `getSerializedNodeId`, `createRandomNodeId`, `resolveNodeIdTransformClasses`, `registerNodeIdTransforms`, `createNodeIdExtension`. Decisions:
    1. **Block types are derived, not hardcoded** — `NODE_ID_BLOCK_TYPES = MARKDOWN_SUPPORTED_NODE_TYPES − NODE_ID_EXCLUDED_TYPES`, where the exclusions (`root`, `text`, `linebreak`, `tab`, `code-highlight`, `link`, `autolink` — root plus inline nodes) each carry a stated reason. A block type added by a future Luthor release joins the covered list automatically and `resolveNodeIdTransformClasses` throws if it cannot be resolved, so it can never be silently skipped (R-12.2).
    2. **Transform classes are resolved from the editor's node registry** (`editor._nodes.get(type).klass`), not imported: `image`, `iframe-embed` and `youtube-embed` have no stable named export, and this guarantees the transform binds the exact class the editor uses. One `registerNodeTransform` per concrete class, as 0.1 required.
    3. **Uniqueness is enforced against a live `nodeId → nodeKey` index, not "assign when absent."** Lexical's `application/x-lexical-editor` clipboard payload carries the `$` state, so pasting blocks copied from the same document reintroduces ids that are still live. The **copy** is re-issued a fresh id and the node that already held it keeps it, so comments already anchored stay anchored. The index is rebuilt from the document on the first transform of each update, because `injectJSON` swaps the node map without running transforms.
    4. **Default generator is random, not a counter.** A counter restarts at 1 on every reload while the loaded document already holds `n1…`; the round-trip test pins that a fresh session's generator never re-issues a live id.
    5. **`nodeId` lands under the `$` key** — `{"type":"paragraph", …, "$":{"nodeId":"…"}}`. Readers must use `getSerializedNodeId(node)` (`node.$.nodeId`), **not** `node.id` / `node.nodeId`; task 3.1's `resolveNode` matches on `id`/`nodeId` and needs adjusting to read `$`.
  - **NEW LIMITATION found (affects 2.3, 7.1, 7.4, 11.x):** `image`, `iframe-embed` and `youtube-embed` get a `nodeId` in memory but it **does not survive serialization**. Luthor 2.9's node classes build `exportJSON()` as an object literal instead of spreading `super.exportJSON()` — and `LexicalNode.exportJSON()` is where Lexical writes the `$` key — and their `importJSON()` constructs a fresh node rather than going through `updateFromJSON`, so neither direction round-trips. Lexical's own decorator nodes are unaffected (`horizontalrule` round-trips). Recorded as `NODE_ID_UNSERIALIZABLE_TYPES`; the R-12.2 test pins both halves (covered by a transform, gap in serialization) so it fails the day Luthor fixes it. Consequence: an image or an embed cannot be a durable comment target yet.

- [x] 5.1 Issue-comment projection into `CommentDoc` (deps: 4.1, est: ~4d)
