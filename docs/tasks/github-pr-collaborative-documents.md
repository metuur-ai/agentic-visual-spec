## Unit 2: Owned node layer

- [x] 2.1 NodeState-based `nodeId` + per-class transforms (deps: 0.1, 1.1, est: ~1w)
  - **RE-SCOPED after task 0.1.** The original title was "Owned block node classes carrying `nodeId`". Task 0.1 proved node replacement cannot keep the base `getType()` on Lexical 0.40, so R-2.2 now mandates Lexical's NodeState API instead. See the amended R-2.2 note in the EARS spec and the superseded-mechanism note in LLD §2.
  - why: serialized Lexical nodes have no stable key. A node transform registered per concrete class is the interception point that covers nodes created *inside* the editor — on Enter, on paste, on list toggle — and NodeState is the only carrier that survives serialization without changing the node's `type`.
  - acceptance: R-2.2 — `nodeId` carried via `createState`/`$setState`/`$getState`, assigned by `registerNodeTransform` per concrete class, not a structural path or sidecar map; R-2.3 — the serialized `type` stays the base string so `MARKDOWN_SUPPORTED_NODE_TYPES` and the transformers keep matching (free under NodeState); R-2.4 — every editor-created node gets a document-unique `nodeId`; R-2.5 — `nodeId` survives `exportJSON()`/`importJSON()`.
  - verify: extend the 0.1 harness (`ui/node-identity.contract.test.tsx`) across every block type in `MARKDOWN_SUPPORTED_NODE_TYPES` (R-12.2). Note `registerNodeTransform` rejects abstract bases like `ElementNode` — one call per concrete class.
  - landed: `ui/node-id-extension.ts` (new) + `ui/node-id-extension.contract.test.tsx` (new, 22 tests). Suite 397 → 419 green, `tsc --noEmit` clean. Exports `nodeIdState`, `NODE_ID_BLOCK_TYPES`, `NODE_ID_EXCLUDED_TYPES`, `NODE_ID_UNSERIALIZABLE_TYPES`, `$getNodeId`, `getSerializedNodeId`, `createRandomNodeId`, `resolveNodeIdTransformClasses`, `registerNodeIdTransforms`, `createNodeIdExtension`. Decisions:
    1. **Block types are derived, not hardcoded** — `NODE_ID_BLOCK_TYPES = MARKDOWN_SUPPORTED_NODE_TYPES − NODE_ID_EXCLUDED_TYPES`, where the exclusions (`root`, `text`, `linebreak`, `tab`, `code-highlight`, `link`, `autolink` — root plus inline nodes) each carry a stated reason. A block type added by a future Luthor release joins the covered list automatically and `resolveNodeIdTransformClasses` throws if it cannot be resolved, so it can never be silently skipped (R-12.2).
    2. **Transform classes are resolved from the editor's node registry** (`editor._nodes.get(type).klass`), not imported: `image`, `iframe-embed` and `youtube-embed` have no stable named export, and this guarantees the transform binds the exact class the editor uses. One `registerNodeTransform` per concrete class, as 0.1 required.
    3. **Uniqueness is enforced against a live `nodeId → nodeKey` index, not "assign when absent."** Lexical's `application/x-lexical-editor` clipboard payload carries the `$` state, so pasting blocks copied from the same document reintroduces ids that are still live. The **copy** is re-issued a fresh id and the node that already held it keeps it, so comments already anchored stay anchored. The index is rebuilt from the document on the first transform of each update, because `injectJSON` swaps the node map without running transforms.
    4. **Default generator is random, not a counter.** A counter restarts at 1 on every reload while the loaded document already holds `n1…`; the round-trip test pins that a fresh session's generator never re-issues a live id.
    5. **`nodeId` lands under the `$` key** — `{"type":"paragraph", …, "$":{"nodeId":"…"}}`. Readers must use `getSerializedNodeId(node)` (`node.$.nodeId`), **not** `node.id` / `node.nodeId`; task 3.1's `resolveNode` matches on `id`/`nodeId` and needs adjusting to read `$`.
  - **NEW LIMITATION found (affects 2.3, 7.1, 7.4, 11.x):** `image`, `iframe-embed` and `youtube-embed` get a `nodeId` in memory but it **does not survive serialization**. Luthor 2.9's node classes build `exportJSON()` as an object literal instead of spreading `super.exportJSON()` — and `LexicalNode.exportJSON()` is where Lexical writes the `$` key — and their `importJSON()` constructs a fresh node rather than going through `updateFromJSON`, so neither direction round-trips. Lexical's own decorator nodes are unaffected (`horizontalrule` round-trips). Recorded as `NODE_ID_UNSERIALIZABLE_TYPES`; the R-12.2 test pins both halves (covered by a transform, gap in serialization) so it fails the day Luthor fixes it. Consequence: an image or an embed cannot be a durable comment target yet.

- [x] 2.2 Version bump + backfill (deps: 2.1, est: ~3h)
  - why: `version` is what distinguishes "same block, edited since the comment" so a comment can be flagged outdated. Backfill covers documents authored before this shipped and any node that escapes the replacement.
  - acceptance: R-2.6 — content change bumps `version`, never `nodeId`; R-2.7 — unchanged content does not bump; R-2.8 — missing `nodeId` backfilled on first write and recorded; R-2.12 — a write that cannot produce unique ids fails rather than persisting a partially identified document.
  - verify: property test over random edit scripts (insert/delete/move/edit) asserting id stability and version monotonicity.
  - landed: `core/collaboration/node-identity.ts` (new) + `core/collaboration/node-identity.test.ts` (new, 25 tests) + `ui/node-identity-parity.test.ts` (new, 2 tests). Suite 533 → 560 green, `tsc --noEmit` clean. Exports `NODE_IDENTITY_EXCLUDED_TYPES`, `isAddressableBlockType`, `collectBlocks`, `nodeContentSignature`, `nodeTextContent`, `NodeIdentityError`, `NodeIdentityRecord`, `NodeIdentityBackfillRecord`, `ReconcileOptions`, `ReconcileResult`, `reconcileDocumentIdentity`, `withNodeIdentity`. Decisions:
    1. **Pure JSON, so it lives in `core/collaboration/`** — nothing here needs a `LexicalEditor`; a serialized node is a plain object, `nodeId` is `node.$.nodeId`, and content comparison is structural. Under `ui/` it would be unreachable from the CLI and the Vite host, which is where writes happen.
    2. **"Content" = the block's whole serialized subtree** — text, formatting marks, attributes and child structure — canonicalized with keys sorted and every `$` key stripped at every depth. Formatting counts (bolding the commented sentence changes what the reviewer sees); identity does not (which is why a backfill can never bump the version it just assigned an id for). A parent's signature contains its children's, so editing a list item bumps both the item and the list.
    3. **Version bumping runs at the store/serialization boundary, not as an editor transform.** A transform fires on every editor update — caret moves, selection changes, re-renders — so it would inflate `version` and flag anchored comments outdated for edits nobody made. The boundary compares exactly two persisted revisions.
    4. **`version` lives on the envelope's `nodes` projection** (`CollaborationNode.version`, LLD §1), not inside the Lexical tree: a field added to the tree is either dropped by the next `importJSON` or, under `$`, editable from inside the editor. `reconcileDocumentIdentity` rebuilds the projection every time and is the single place `version` is defined.
    5. **The backfill record is an envelope field, `identity.backfill = { at, nodeIds }`**, cumulative. It is a durable property of the document, not of a run: a machine-assigned id is not the id any earlier comment anchored to, and a consumer investigating an orphan needs the whole set, not the last batch. A job event would be gone by the time anyone asks. The record is only rewritten when something was actually backfilled, so a reconcile on every load does not churn the file.
    6. **Backfill does not churn `version`** — the content signature ignores `$`, so assigning an id changes no signature; and a newly identified block has no counterpart in the previous revision, so it starts at `version: 1` rather than bumping. Second pass over the same document is a no-op (test pins it).
    7. **R-2.12 fails, it does not repair.** Two live blocks sharing a `nodeId` throw `NodeIdentityError` — at this boundary there is no way to tell which one a comment was anchored to, and `registerNodeIdTransforms` already de-duplicates inside the editor where the copy *is* identifiable. A generator that cannot produce an id unique against the live document within 50 attempts throws too. `withNodeIdentity(store).write` throws before `store.write` is called, so nothing partially identified is persisted (test asserts the inner store is never touched).
    8. **`withNodeIdentity(store)` is the wiring point** — a decorator over any `DocumentStore` so the same rules hold for the GitHub-backed store (3.2). `read` backfills in memory and does not write back (a read that commits is unacceptable on a PR branch; backfill is a repair mechanism, LLD §2), `write` bumps against the previously persisted revision. `fsDocumentStore` itself is unchanged.
    9. **The exclusion list is stated twice on purpose.** `core/` cannot import `ui/node-id-extension.ts` (it pulls Luthor, R-3.3), so `NODE_IDENTITY_EXCLUDED_TYPES` mirrors `Object.keys(NODE_ID_EXCLUDED_TYPES)`; `ui/node-identity-parity.test.ts` is the only file allowed to import both and fails if they drift.
    10. **Property test**: 200 seeded cases (mulberry32, seeds 1…200, no `Math.random()`) × 12 random ops from insert / delete / move / edit / no-op, over paragraphs, headings and quotes-with-nested-paragraphs. Logical identity is tracked out-of-band through a `$.marker` (stripped from the signature) so id stability cannot be true by construction. Per step it asserts: every block identified and no id shared; the projection covers every block; ids of surviving blocks unchanged across insert/delete/move/edit; `version` never decreases; `version` increments **exactly** when the content signature changed and is otherwise unchanged; `bumpedNodeIds` agrees with the signatures; new blocks start at 1; and every backfilled id appears in `identity.backfill.nodeIds`. On failure it prints the seed and the operation log. Killed three deliberate mutants (never bump, always bump, always re-issue ids).

- [x] 2.3 Publish payload generator (deps: 2.1, est: ~4h)
  - why: `json` and `markdown` must come from **one** object at **one** instant. The server treats the Markdown as opaque, so no server-side check can catch a client that serialized the two from different states — this invariant is the only thing preventing a silent mismatch.
  - acceptance: R-2.9 — uses `jsonToMarkdown(doc, { metadataMode: 'none' })`; R-2.10 — generated Markdown is write-only, never parsed back; R-2.11 — editor driven through `getJSON()`/`injectJSON()`, not a Markdown string buffer.
  - verify: R-12.8 — test asserts both artifacts derive from the same document object via a single call. Explicitly **not** reusing `normalizeForStore(getMarkdown())` (`ui/wysiwyg-editor.tsx:135`), which reads live editor state and applies local-viewer image rewriting.
  - landed: `ui/publish-payload.ts` (new) + `ui/publish-payload.test.ts` (new, 11 tests). Suite 533 → 544 green, `tsc --noEmit` clean. Exports `generatePublishPayload`, `PublishPayload`, `PublishDocumentSource`, `DroppedNodeReport`. Decisions:
    1. **The function takes a reader, not a document, and calls it exactly once.** `generatePublishPayload(() => editorRef.current.getJSON())`. Taking a reader is what makes the single-instant invariant testable: the R-12.8 test rigs a source that returns a *different* document on every call, so a hypothetical second read of live editor state would surface as `markdown` describing a document `json` does not. A signature that took a document object could only ever assert "both fields exist".
    2. **The one read is immediately detached** — `JSON.parse` for the `getJSON()` string, `structuredClone` for a document object — so an edit landing after the call reaches neither artifact. `markdown` is then always exactly `jsonToMarkdown(payload.json, { metadataMode: 'none' })`, which is verifiable after the fact.
    3. **Dropped nodes are surfaced, not silently lost.** `prepareDocumentForBridge(json, { mode: 'markdown', supportedNodeTypes: MARKDOWN_SUPPORTED_NODE_TYPES })` is used for **detection only**: its envelopes become `payload.droppedNodes` (`{ nodeId?, type, path, fallback }`, `nodeId` read via `getSerializedNodeId` off the `$` key) and are never appended to the output. Verified empirically that the `$` key itself produces no envelopes, so `nodeId` never pollutes the report.
    4. **`normalizeForStore(getMarkdown())` is not reused** for two independent reasons: it is a *second* read of live editor state (the divergence this task exists to prevent), and it rewrites image `src`s for the local viewer, which is meaningless in a published artifact.
    5. **The three unserializable types are a non-issue here.** `image`, `iframe-embed` and `youtube-embed` lose their `nodeId` on export, but publishing never reads `nodeId`, and all three are in `MARKDOWN_SUPPORTED_NODE_TYPES` so they are never dropped. A test pins that membership.

- **O-11 — `visual-spec init` scaffolds a dead config file.** `template/visual-spec.config.ts` is copied into every new project and documented at `README.md:63,87`, but nothing loads it: the template's own `vite.config.ts` calls `visualSpec()` with no arguments, and the file's `spec: { mode, defaultDialect }` key is not even in the `VisualSpecConfig` type. ### Settled — decisions taken, so they are not reopened

- **O-8 — the drive-by reviewer: two buckets, not three. No code change.** 9.2 classifies from write access, and that binary *is* the role model: write ⇒ author, no write ⇒ comment-and-reply. A drive-by commenter on a public repo has no repo access and lands in the second bucket, which is where they belong — every author-only route is authorized server-side by `hasWriteAccess`, and issue comments genuinely need no repo access, so the accidental resolution and the intended one are the same resolution. Rejected: a third role bucket (it would have to be derived from something GitHub does not report — "read access" on a public repo is indistinguishable from none), and requiring collaborator-with-read (it would break the public-repo review case the product wants). What was actually missing was wording, not classification: the snapshot says *review-only session* to anyone without write, and onboarding must state that commenting needs no repo access while publishing needs write. That sentence is 12.2's to write.

## Unit 13 — reviewing a pull request's code (in flight)

### Landed

- **`core/collaboration/worktree.ts`** — mount/list/unmount a PR's tree at
  `.visual-spec/worktrees/pr-<n>`, detached, fetched via `refs/pull/<n>/head` so fork
  PRs work. `ensureIgnored` writes the ignore entry before the first mount. 16 tests
  against real repositories.
- **`listPullRequests`** on the GitHub adapter, paginated like the comment lists.
- **`core/collaboration/review-drafts.ts`** — held comments at
  `.visual-spec/reviews/pr-<n>.json`, `d-<8hex>` ids, `headSha` on every draft. 17 tests.
- **`/pulls/*` routes** in the collaboration router, above the document-scoped match.
  26 tests. Suite at 949 green.

### Findings worth keeping

- **A misordered `/pulls` route fails silently, not loudly.** The premise going in was
  that placing it below the document-scoped match would yield
  `bad('invalid documentId: pulls')`. False: `DOCUMENT_ID_RE` is `/^[a-z0-9][a-z0-9-_]*$/i`
  and `pulls` satisfies it, so the request would be answered **200** as the status
  snapshot of a document named "pulls" — nothing at all from the client's side. The
  ordering constraint is therefore load-bearing in a way a 400 would not have been, and
  it is asserted both behaviourally and by source index.
- **One worktree, two spellings.** `mount` reported `join(baseDir, rel)` and `list`
  reported git's resolved path; under `/tmp` on macOS those differ (`/private/tmp`), so
  "is this PR mounted?" answered no. Fixed by asking git for the canonical path. The
  test now asserts `mount ≡ list` rather than a literal path — a literal path is what
  let it through.
- **R-13.16 is not closed by the store alone — now closed by the route.**
  `markDraftPublished` is first-write-wins *on disk*, but it runs **after** the network
  call, so on its own it would record one id while GitHub had been handed two comments.
  The gate is the publish route re-reading the record from disk and short-circuiting on
  `status !== 'draft'`, answering 200 with `alreadyPublished: true` rather than an error
  — a 4xx would push clients into retrying the thing that must not repeat. Asserted by
  counting adapter calls (exactly one across two requests), and again through a fresh
  router over the same directory so the gate is provably the disk read and not process
  memory. The same-process millisecond race stays open, matching the lock-file rejection
  argued in `review-drafts.ts`.

### Two defects the suite could not have found

- **`.git` was browsable in every checkout.** A linked worktree carries `.git` as a
  *file* holding `gitdir: …`, not a directory, so the `.git/` ignore pattern missed it.
  Fixed by listing the bare name too; the regression was confirmed to fail without the
  fix before being kept.
- **Markdown files could not be commented on.** The rendered surface has no lines and a
  comment anchors to one, so the composer was unreachable on exactly the files this
  product exists to review. Fixed with a rendered/source toggle on the review surface;
  flipping it clears any pending selection, so no composer outlives the line it names.

Both were found by driving a real pull request in a browser. Neither was visible to
1,264 passing tests.
