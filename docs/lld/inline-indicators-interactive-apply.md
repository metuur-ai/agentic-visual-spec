# Inline Comment Indicators + Interactive Apply Review — Low-Level Design

Source paths are relative to `packages/visual-spec/`. (These spec docs live at the **repo root** `docs/`, not `packages/visual-spec/docs/`.) Line references reflect the state captured in `.devlocal/research/2026-07-14-inline-indicators-interactive-apply.md`.

## Architecture

Two additive subsystems: **(A) inline indicators + reverse navigation** (frontend only) and **(B) interactive review session** (new backend hub + routes + prompt, new frontend review UI). The existing bulk apply path is untouched.

### A. Inline indicators (View mode) + reverse navigation — SHIPPED

Built and merged (`cf68d62`, rewired to node identity in `221bd1e`). The modules are `ui/indicator-layer.tsx`, `ui/indicator-model.ts`, `ui/anchor-resolver.ts`, `ui/active-comment.tsx`; tasks A1.1–A2.1 are complete. The design notes below are kept as the record of intent — read them against the shipped modules, not as work to do. One addition the original text predates: the collaborative surface supplies `IndicatorTarget`s resolved by node identity rather than by line.

- **Data source.** Reuse `useComments(path)` (`core/app/lib/use-comments.ts:36-88`), filtering to `status === 'open'` for the current file. No new fetch.
- **Anchoring.** An `IndicatorLayer` renders one marker per open comment, positioned against the existing DOM anchors:
  - Markdown View: `[data-vs-loc^="${startLine}:"]` inside `[data-inspector-root]` (`ui/markdown-surface.tsx:41-51,108`).
  - Code View: `[data-line="${startLine}"]` and its gutter span (`ui/code-view.tsx:57,61`).
  - The marker is an overlay/gutter affordance keyed to the anchor element, kept glued as layout shifts. `InspectOverlay` tracks 1–few frames per `requestAnimationFrame` (`inspect-overlay.tsx:88-101`); for potentially many indicators, use a **single shared rAF loop batching all indicator positions** and/or an `IntersectionObserver` so only on-screen anchors are tracked — avoids per-indicator rAF jank on large files. Indicators are visually distinct from the transient `flash()` highlight and from selection frames.
  - Multiple open comments on the same line collapse into one indicator carrying a count.
- **Marker resolution reuse.** Indicator placement uses the same target→element resolution already implemented in `locate()` (`ui/comment-history-list.tsx:28-47`) and `locateLine()` (`ui/generic-panel.tsx:157-172`); extract the resolver so both `locate()` and `IndicatorLayer` share it (no behavioral change to `locate()`).
- **Reverse navigation (document → sidebar).** Introduce an **active-comment** state (a small context or lifted state consumed by `CommentPanel`/`GenericPanel`). Clicking an indicator sets the active comment id; the sidebar scrolls that row into view and applies a highlight. This is the inverse of today's sidebar → document `locate()`, which has no counterpart yet. The sidebar remains the primary surface for viewing/filtering/managing comments — the indicator only points into it.

### B. Interactive review session

- **ReviewHub (new), `core/vite/routes/review.ts`.** Mirrors `ApplyHub` (`core/vite/routes/apply.ts:237-305`): a single-session, in-memory, ephemeral hub holding `{ session, events[], phase, startedAt, abort, subs }`.
- **Shared single-session lock (`RunLock`).** `ApplyHub` holds a *private* `running` flag in its closure (`apply.ts:253`); a second hub built "mirroring" it would get its **own** flag, so review and bulk apply could run concurrently and race on the sidecar. To make mutual exclusion real, introduce a small shared `RunLock` module both hubs consult (injected via the same `getDeps` thunk they already use). `ApplyHub.start` and `ReviewHub.start` both acquire it and both return 409 if held; the 409 body names *which* holder rejected (review-running vs apply-running) so the UI can message correctly. This is a one-line addition to the existing `applyHub.start` path — the bulk flow's behavior is otherwise unchanged.
- **Session lifecycle & slot release on all exit paths.** Unlike `runApply` (a single awaited promise releasing the lock in `.finally()`, `apply.ts:290`), a review session is long-lived with turns arriving asynchronously via `POST /message`. The `RunLock` must therefore release on **every** terminal path: explicit cancel (SIGKILL), child `close`/`error`, an idle/lifetime timeout (reuse the 15-min SIGKILL precedent at `apply.ts:187`), and **abandonment** — no subscribed client and no input for N minutes (a dropped browser tab must not wedge the slot until restart).
- **Transport.** A persistent `claude` child spawned with `--print --input-format stream-json --output-format stream-json --replay-user-messages` and `stdio: ['pipe','pipe','pipe']` (stdin **piped**, unlike today's `'ignore'` at `apply.ts:81`). Output is parsed by the existing `summarize()` stream-json reader (`apply.ts:85-138`, extract/share it). Follow-up turns are written to the child's stdin as stream-json user messages; `--replay-user-messages` echoes them on the out-channel so the transcript is a single ordered log. A cost guardrail (e.g. `--max-budget-usd`) bounds an open-ended session, complementing the wall-clock timeout.
- **Read-only enforcement — at the permission layer, not the prompt.** The propose phase runs with `--permission-mode plan`, which blocks edits **to the workspace** at the permission layer (verified by spike 0.2's control arm: identical approval wording without the control frame produced no write). It is not a global no-write — the CLI still writes its own plan files under `~/.claude/plans/` — but the workspace is what R-3.7 and R-4.7 protect. "Started without `acceptEdits`" is **not** sufficient — default mode still permits edits and merely prompts, which is undefined in headless. For defense in depth, `--allowedTools` may additionally exclude Write/Edit. The prompt is not a security boundary; it only shapes proposal content.
- **The proposal IS the patch — fidelity is structural, not checked after the fact.** The defect this replaces: a proposal produced in plan mode describes a change the model never made, and *both* previously specified approval paths re-derive the edit rather than replay it — the scoped write pass runs `buildApplyPrompt` in a **fresh process** carrying the comment, not the diff (`apply.ts:161`, `:80`), and an in-session write regenerates from context. The user approves run A and receives run B, with nothing detecting it. `R-6.3`'s drift check does not close this: it asks whether the *target content* changed, not whether the *written bytes* match what was approved.
  - The `proposal` envelope therefore carries a **machine-applicable unified diff**, not a narrated one. Approval applies *that patch* — `git apply` through the existing `GitExecutor` (`core/git-context.ts:68`), which is already wired as a subprocess executor, so no new dependency. The approved artifact and the applied artifact are then the same object by construction.
  - Stale-diff reconciliation collapses into "the patch did not apply cleanly" — a real, cheap, unfakeable check that subsumes both the local content-drift case and the collab node-drift case.
  - This removes the hard dependency on mid-session write escalation: the process that writes is the server, not the model. Applies identically to local and collab, which matters because **collab has no `/apply/start` fallback**.
  - Retained as a fallback for local mode only, if a patch proves unable to express an edit: the scoped write pass via `POST /apply/start { ids:[commentId] }` (`apply.ts:279-294`). It re-derives, so it must not be presented to the user as "applying the approved diff" — see the fidelity requirement in EARS Unit 6.
- **Mid-session escalation — proven, but unsupported (spike 0.2 passed).** A plan-mode session *can* be lifted to write mid-process, via the undocumented `control_request` subtype `set_permission_mode` on the stream-json stdin channel. B4.4 is therefore viable. It stays an optimization rather than the default: the subtype appears in no `--help` output and can break on any CLI update, so it is a version-pinned capability. Patch application (B4.1) remains the standing write mechanism, and is the only one available to collab mode.
- **Scoped writes have a global side effect (pre-existing, inherited).** `runApply` re-reads the sidecar after the run and stamps `Applied successfully.` onto **every** applied comment missing a `result` across the whole store, not just the run's `ids` (`apply.ts:214-226`). A single-comment review approval that routes through the fallback therefore mutates unrelated records. Pre-existing, but the review path makes it reachable from a single-comment action — scope the stamping to the run's id set when touching this code.
- **Comment origin — two edit targets in one session.** `CommentOrigin` / `CommentTargetKind` (`core/editing/comment-doc.ts`) already carry local-vs-collaborative provenance through the UI, and `buildApplyPrompt` already branches on `{ mode: 'local' } | { mode: 'collab'; documentPath }` (`core/editing/apply-prompt.ts:43`). `buildReviewPrompt` takes the same discriminated option so the review session inherits the branch instead of inventing a second one:
  - **local** — target located by snippet + heading, edited in place; on approval the comment flips `open → applied` with a `result` (below).
  The two arms differ in five places — comment source, target resolution, drift check, terminal state, and fallback availability — so do **not** thread a raw `mode` field through route body, hub, prompt, and write path or you get `if (mode === 'collab')` at five sites. Define one narrow hub-level interface (`resolve` → `locate` → `checkDrift` → `finish`) with a local and a collab implementation, and keep the plain discriminant only where it already lives: the prompt. Equally, do **not** build a strategy/store abstraction for a two-member union — one interface, two implementations, no registry.
  - **collab** — target located by `collab.nodeId` (exact lookup, no snippet/line fallback; a comment with no nodeId is document-level). The only editable file is the canonical JSON at `documentPath`; generated Markdown is write-only output. **No status or result is written to any file** — resolution is recorded on the conversation. The run ends with the exact terminal line `PUBLISH_HANDOFF_PREFIX + documentPath` (`apply-prompt.ts:50`), which the ReviewHub matches to emit a `ready-to-publish` frame. The agent must not publish.
- **Collab needs an apply/review server path (build dependency).** What is missing is narrower than "no server surface": `core/collaboration/` already has a 116KB `collab.ts`, a publish path, a record store, the review-drafts lifecycle, and — most relevant here — `core/collaboration/job-hub.ts`, which already runs long-lived jobs with an event stream. What does not exist is an *apply* path: `copyHandoff` (`ui/collab-app.tsx:370-386`) builds the collab prompt and writes it to the clipboard, by an explicit deferral ("No route, no process, no activity stream — those are worth building once the prompt is known to be good"). `copyHandoff` stays as the manual escape hatch.
  - **Open architectural question, decide before B1.2:** does `ReviewHub` sit beside `ApplyHub` in `core/vite/routes/`, or reuse `job-hub.ts`? Reuse would inherit the long-lived-job + event-stream machinery the hub otherwise reimplements, but couples the local review path to the collaboration module. Resolve this in the first backend task, not after.
- **Where a collab review session gets its comment (contract hole — was unspecified).** `POST /review/start { commentId, documentPath }` is not sufficient. Collab comments are **projected at runtime** — `projectIssueComment` (`core/collaboration/comment-projection.ts:136`) and `projectReviewThread` (`core/collaboration/review-comments.ts:282`) mint ids via `recordIdFor` / `reviewRecordIdFor` from the GitHub comment id — so the record exists only in the client's projection. The id alone identifies neither repo nor pull request, no route resolves a collab comment by id (`createCollabRoutes`, `core/vite/routes/collab.ts:879`, serves only `/__vs/collab/{open,pulls,start}`), and `R-9.1` forbids falling back to the sidecar. Two options, pick one in B1.2:
  - **(a) Client-supplied record (preferred).** The start body carries the projected record itself — `{ documentPath, comment: { id, nodeId, text, workflow } }`. No new resolution route, no server-side GitHub round trip, and it matches how `copyHandoff` works today (the client already holds everything the prompt needs). Cost: the server trusts client-supplied text, which on an unauthenticated localhost route is the same trust boundary the existing routes already assume.
  - **(b) Server-side resolution route.** Add `/__vs/collab/comment/:id` taking repo + PR context, re-fetch and re-project server-side. Faithful, but adds a route, a GitHub call on the approval path, and a second projection site that can drift from the first.
  This changes the `R-8.8` contract; the EARS statement is written against (a).
- **Stale-diff reconciliation.** The diff shown in propose is computed against file state at propose time; between propose and approve the file may change (the sidecar is treated as mutated out-of-band, research §2.4) and the fallback's fresh write pass may regenerate a *different* change. Before writing, THE apply step re-resolves the target by snippet+heading; if the anchor has drifted or the target content changed since the proposal, it **surfaces the drift and requires re-approval** rather than applying a stale diff. With the patch-as-artifact mechanism above, the primary detection is simply that `git apply` refuses the patch — the check is structural rather than heuristic.
  - **Collab drift = head SHA, not content compare.** The canonical document lives on a branch, so pin `headSha` at propose time and compare at approve time. This is the guard `core/collaboration/review-drafts.ts` already uses — `isStale(draft, headSha) => draft.headSha !== headSha` (`:399`) — and it is stronger and cheaper than diffing node content. Note what is *not* reusable: `review-drafts.ts` is a SHA compare over a **persisted** record and has no "did this node's content change" primitive, so only the head-SHA idea transfers, not the module.
  - Additionally, if the target `nodeId` no longer exists in the canonical document, surface drift rather than writing.
- **Prompt, `core/editing/review-prompt.ts` (new).** `buildReviewPrompt(comment)` instructs the model, for one comment resolved by snippet+heading (same locating rules as `apply-prompt.ts:15-17`), to: state its interpretation, strategy, reasoning, assumptions/ambiguities, alternatives when appropriate, an expected unified diff, and estimated impact. Because plan mode already blocks edits, the prompt focuses on proposal *content*, not on asking the model not to write. The proposal is emitted against a pinned structure (via `--json-schema` for the proposal envelope) so the structured `proposal` frame fields are populated deterministically rather than parsed from prose. Shares the comment-manifest formatting with `buildApplyPrompt` where practical.
- **Routes (new), registered in BOTH `core/vite/md-plugin.ts` and `src/server.ts`** (dual-server rule):
  - `GET  /__vs/review/events` — SSE subscribe; first frame a `sync` replay (as `apply.ts:275`).
  - `POST /__vs/review/start   { commentId }` (local) or `{ commentId, documentPath }` (collab) — begin propose phase; the body's shape selects the prompt mode and the approval path. On lock contention returns 409 with a body naming the holder (review-running vs apply-running).
  - `POST /__vs/review/message { text }` — inbound follow-up → child stdin (the missing in-channel).
  - `POST /__vs/review/approve` — authorize write; produce diff-applied result (subject to stale-diff reconciliation).
  - `POST /__vs/review/cancel`  — SIGKILL child, release lock, discard session, comment stays `open`.
  - `GET  /__vs/review` — `{ running, startedAt, commentId }` status snapshot, mirroring `GET /__vs/apply` (`apply.ts:16`). Without it a reloaded tab cannot discover an in-flight session before subscribing, and the abandonment timer (`R-7.6`) can reap a session whose only client is mid-reload.
  - **Dead-child race:** if a `message`/`approve` arrives after the child died but before the slot released, respond with a distinct status the UI can tell apart from "no session" (`R-7.7`).
- **Event types.** Extend the streamed union with review-specific frames: `proposal` (structured envelope pinned via `--json-schema`: interpretation/strategy/assumptions/alternatives/diff/impact), `awaiting-input`, `applied`, `drift` (stale-diff → re-approval), `ready-to-publish` (collab terminal handoff, carrying `documentPath`), alongside reused `log`/`error`/`done` shapes (`apply.ts:24-37`), so `summarize()`'s output type stays exhaustive.
- **Entry point (missing today).** There is no per-comment "Apply Comment" affordance. `ui/main-header.tsx:1223-1230` is the only caller of `/apply/start` and it is the bulk scope chooser. `R-3.1` presumes a trigger nothing builds, so a per-comment action on the sidebar row (and, for collab, on the collab panel row) is in scope for the review UI work.
- **Frontend review UI (new).** A review view (in or beside `CommentPanel`) that: subscribes to `/__vs/review/events` via `EventSource` (as `main-header.tsx:255-280`), renders the proposal and streamed diff, offers a follow-up input (`POST /message`), and Approve/Cancel buttons. On `applied`/`done` it dispatches `vs:comments-changed` + `vs:source-changed` (as `main-header.tsx:270-272`) so the doc and sidebar refetch.
- **Status/result.** In **local** mode, on approval+apply the comment flips `open → applied` with a `result` via the existing `PATCH /__vs/comments/:id { status, result }` (`comments.ts:121-124`); no new comment field is persisted (session is ephemeral). In **collab** mode nothing is written to the sidecar — the session ends at `ready-to-publish`.
  - **Closing the collab loop (was left dangling).** "The conversation records resolution" named a mechanism nothing implemented: `projectIssueComment` (`comment-projection.ts:156`) and `projectReviewThread` (`review-comments.ts:294`) both hardcode `status: 'open'`, so after an approved collab apply the comment re-projects as open, `R-1.11` keeps rendering its indicator, and the user can review it again. The fix is **not** to derive status from GitHub's `isResolved` — `review-comments.ts:274-281` rules that out explicitly (R-5.21): `status` records whether the *local apply agent* has acted, and deriving it from remote resolution reintroduces a second resolution model and lets a local value be mistaken for a remote one. Instead the session **posts a reply on the review thread** recording what was applied, which is the record a human reviewer reads. The comment staying locally `open` until publish is then correct by design, not a leak — but it must be stated, because it looks identical to the bug. `CommentStatus` stays the two-value union at `core/editing/comment-doc.ts:14`: it is parsed defensively (`:86`, `?? 'open'`), persisted to `visual-spec-comments.json`, and encoded into GitHub comment bodies via `formatCommentBody` / `parseCommentBody` / `CommentTrailer`, so a third value would be a wire-format change across both stores. In-flight review state lives in the hub, not on the record.

## Constraints

- **Dual server.** Every route must be registered in both `core/vite/md-plugin.ts` (dev) and `src/server.ts` (prod); handlers should be shared like `handleCommentsRequest`.
- **Streaming = SSE only, out-direction.** Inbound turns use a separate `POST /message` writing to child stdin; there is no bidirectional socket. Headers follow the existing SSE pattern (`apply.ts:269-274`).
- **`claude` CLI dependency.** Interactive review requires a `claude` binary that supports `--input-format stream-json` multi-turn on stdin. Auth rides on the CLI (no API key), matching today (`apply.ts:75`).
- **Indicators are View-mode only.** WYSIWYG/CodeMirror anchoring is out of scope; the code must not assume `data-vs-loc`/`data-line` exist in Edit modes.
- **No auth** on `/__vs/*`; localhost assumption unchanged.
- **Collab mode may not touch the sidecar.** In a collaborative session `visual-spec-comments.json` is a non-authoritative cache (R-5.3); the review prompt must not read, edit, or trust it, and the generated Markdown is write-only output that must not be edited.
- **What `local-mode.regression.test.ts` actually pins** (an earlier draft of this LLD got this backwards). The R-10.5 guard is a fixed **module list**, not a blanket rule, and `apply-prompt.ts` already carries the whole collab branch (`collabInstruction`, `nodeId`, `documentPath` at `:55-57`) and passes it. So sharing a module with `apply-prompt.ts` inherits a *narrow* constraint and a separate file inherits *none* — module choice is not the safety question. The real hazards are two other pins:
  - `:377-383` pins `buildApplyPrompt`'s **output** in local mode against `/github|pull request|\bPR\b|documentId|nodeId/i`. A shared manifest formatter must keep every collab field behind the mode branch or local-mode output starts failing.
  - `:423-425` pins the literal source strings `import { buildApplyPrompt } from '../../editing/apply-prompt'` and `spawnClaude(buildApplyPrompt(open), deps.cwd)` in `apply.ts`. Extracting `summarize()` is safe; editing that spawn line is a build break.
  - Decision: `review-prompt.ts` is a **separate module** sharing only the comment-manifest formatter, and both it and `review.ts` are added to the R-10.5 module list deliberately rather than by inheritance.
- **Single active session** for both bulk apply and review — a review must not run while a bulk apply runs, and vice versa (shared guard or mutual 409).

## Key Decisions

- **Indicator scope = View mode only.** Reuses ready anchors and `locate()`; avoids the two greenfield Edit-mode substrates. Rejected: all-modes (largest risk, no precedent) and View+Source (adds CodeMirror gutter decorations now) — both deferrable.
- **Transport = persistent `claude` with `--input-format/--output-format stream-json`, stdin piped.** Reuses the existing `stream-json` parser and keeps auth on the CLI. Rejected: Agent SDK (new dependency + auth path) and stateless per-turn `claude -p` re-invocation (resends full transcript each turn, loses session/tool state). **Verified:** the spike confirmed persistent multi-turn against the bare CLI (flags `--input-format stream-json`, `--replay-user-messages`, `--permission-mode plan` exist on `claude 2.1.170`; process survives its first `result` frame and answers a second turn without writing). The Agent SDK rejection therefore stands.
- **Decision (a): `ReviewHub` sits beside `ApplyHub` in `core/vite/routes/review.ts`; `core/collaboration/job-hub.ts` is not reused.** `job-hub.ts` states in its own header that it mirrors `createApplyHub`'s *discipline* but deliberately not its *shape*: it is a registry keyed by document, several jobs live at once, and it has no global single-slot rule because collaboration does not want one. A review session is the opposite — exactly one, process-wide, mutually exclusive with a bulk apply through the shared `RunLock`. Reusing the registry would mean building the single-slot invariant on top of a container whose purpose is to not have one, then owning both. The decisive cost is identity rather than shape: `job-hub.ts` is keyed by a collaboration document id, and the R-10.5 guard in `local-mode.regression.test.ts` — which `review.ts` was added to deliberately — forbids that identity anywhere on the local review path. Rejected: reusing `job-hub.ts` (inherits lifecycle machinery the hub only partly needs, at the price of coupling the local path to `core/collaboration/`). The remaining duplication is ~30 lines of SSE fan-out shared with `apply.ts`; extracting it is a later refactor of two modules, not a reason to adopt a third one's shape.
- **Decision (b): one hub-level interface, `ReviewSessionOps`, two implementations.** `resolve(commentId)` → `locate(comment)` → `checkDrift(located)` → `finish(comment, outcome)`, plus a `fallbackAvailable` property — the five local/collab differences (comment source, target resolution, drift check, terminal state, fallback availability) named once. The hub calls the interface and never learns which arm it holds; the plain `mode` discriminant stays only where it already lives, in the prompt. `createLocalSessionOps` is the only implementation today: the comment comes from the sidecar store, the target is the file it names, `checkDrift` compares a SHA-256 pin of the target's bytes taken at propose time, `finish` flips `open → applied` through the existing `setStatus` touching no other record, and `fallbackAvailable` is `true`. Phase C adds the collaborative implementation and the hub does not change. No strategy registry and no plugin system — a two-member union gets an interface, not infrastructure. Note on drift: the local `checkDrift` is the *pinned-state pre-check*; once approval applies a patch (B4.1), the patch refusing to apply is the primary unfakeable signal. They are not competing answers — the cheap one runs first.
- **Build order = local review first, collab second.** With the transport proven, the ordering risk moves from the write path to the collab surface: local review reuses routes and stores that exist, collab review must first land the deferred server surface (`copyHandoff` is clipboard-only today). Build and ship local end to end, then extend the hub and prompt to collab. Superseded: the earlier "fallback first" ordering, which existed to avoid building on the unverified transport.
### Spike results (2026-08-22, re-run and retained)

**0.1 — persistent stream-json transport: PASS (3/3).** Ran `claude --print --input-format stream-json --output-format stream-json --permission-mode plan` (CLI 2.1.220) with two user messages on one stdin. (a) The process stayed alive past its first `result` frame; (b) turn 2 was answered correctly from turn-1 context, same `session_id`; (c) the workspace file's sha256 was unchanged. A second `system/init` frame is emitted per turn — the process re-inits but keeps the session. The Agent-SDK rejection stands. Script: `.devlocal/spikes/0.1-transport.mjs`.

**0.2 — mid-session escalation: PASS, a mechanism exists.** `--help` documents none, but the CLI binary implements a `control_request` subtype `set_permission_mode`. Writing `{"type":"control_request","request_id":"…","request":{"subtype":"set_permission_mode","mode":"acceptEdits"}}` to the stream-json stdin returned `control_response {subtype:"success", response:{mode:"acceptEdits"}}`, after which the next turn performed a real `Edit` and the file changed on disk. A control arm with identical approval wording and **no** control frame did not write ("plan mode is still active … regardless of in-conversation approval") — so the frame, not the prompt, is what lifts the mode. **B4.4 is technically viable.** Risk: the subtype is undocumented and can break on any CLI update, so treat it as a version-pinned capability with the patch-apply path (B4.1) as the standing fallback. Script: `.devlocal/spikes/0.2-escalation.mjs`.

**Correction — plan mode is workspace-scoped, not a global no-write.** Both 0.2 arms emitted a `Write` under plan mode to `~/.claude/plans/*.md`, and those files were really created. What plan mode guarantees is that the **workspace** is not edited, which is what R-3.7 and R-4.7 actually need; the earlier phrasing "makes file-editing tools unavailable" was too strong and is corrected in the EARS spec. Also: `ExitPlanMode` was **not** available in `--print` sessions, so the "the model routes through `ExitPlanMode`" note below does not hold for this transport — approval is signalled by the control frame or by the server applying the patch, not by the model exiting plan mode.
- **Read-only via `--permission-mode plan`** (not the prompt) — makes edit tools unavailable at the permission layer. Rejected: relying on prompt instructions (not a boundary) and "no acceptEdits" alone (default mode still permits edits).
- **Preview = model-produced diff, read-only until approval.** The propose phase emits a diff without touching disk; approval authorizes the write. Rejected: dry-run-to-scratch/worktree (faithful but many moving parts) and narrated-plan-only (user approves without seeing exact changes).
- **Session persistence = ephemeral, server-held.** Mirrors `ApplyHub`; comment stays `open` until approved. Rejected: persisting proposal/transcript on the comment record (schema + migration cost) for v1.
- **Reverse-nav via new active-comment state.** Minimal lifted state / context consumed by the sidebar; no change to `locate()` semantics.

## Out of Scope

- Edit-mode (WYSIWYG/Source) inline indicators.
- Proposal/transcript persistence and resumable sessions across restart.
- Concurrent/multi-user review sessions.
- Changes to the bulk apply flow, comment data-model anchoring, or route auth. Bulk apply keeps `acceptEdits` fire-and-forget with no preview gate; the shared `RunLock` is the only edit to it.
- Widening `CommentStatus` past `open | applied`, and any change to `formatCommentBody` / `parseCommentBody` / `CommentTrailer`.
- Automated publishing on a collaborative document. Approval ends at `ready-to-publish`.
- A preview or approval gate on the other server writers (`core/vite/routes/files.ts` create/rename/upload).
- A general bidirectional websocket transport (kept to SSE-out + POST-in).
